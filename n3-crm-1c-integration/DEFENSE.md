## 1. Рассказ за 1 минуту
«Учебный кейс на типовую задачу “интеграция CRM с 1С”. Я начал не с API, а с вопросов: что передаём, в какую сторону, как часто и кто источник истины по каждому полю. Решил обмен через очередь: 1С бывает недоступна, а счёт должен создаться гарантированно. Защита от дублей — внешний ID счёта, равный ID сделки. Реквизиты после создания — только в 1С, чтобы системы не перезаписывали друг друга».

## 3. Вопросы и тезисы
| Вопрос | Тезисы |
|---|---|
| Почему очередь, а не REST-вызов из CRM? | Развязка по доступности, повторы, не теряем события; минус — задержка и дубли |
| Kafka или RabbitMQ? | Для 600 событий в месяц хватит RabbitMQ (очередь задач); Kafka — когда поток большой, нужно хранить и перечитывать события |
| Что такое at-least-once и чем грозит? | Сообщение придёт минимум один раз, возможно дважды → потребитель должен быть идемпотентным |
| Что если менеджер изменил сделку после счёта? | Автоматически не перевыставляем — задача бухгалтеру; счёт — документ учёта |
| Почему адаптер делает GET сделки, а не берёт данные из события? | Событие может устареть; берём актуальное состояние на момент обработки |
| Как найти контрагента? | ИНН+КПП; один ИНН с разными КПП — филиалы |

## 7. Глоссарий
| Термин | Своими словами |
|---|---|
| CRM | Система продаж: клиенты, сделки, задачи менеджеров |
| 1С:УТ | 1С:Управление торговлей — учёт продаж, склада, счетов |
| Адаптер | Промежуточный сервис, который переводит данные одной системы в формат другой |
| Очередь сообщений | Буфер: отправитель кладёт сообщение, получатель забирает, когда может |
| Dead-letter | «Отстойник» для сообщений, которые не удалось обработать после всех повторов |
| Источник истины | Система, которой верим при расхождении |
